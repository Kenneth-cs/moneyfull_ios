# AI 项目归属策略

## 一、4层漏斗机制（优先级从高到低）

```
用户输入 → 第一层（直接指令）→ 第二层（活跃项目⭐）→ 第三层（记忆规则）→ 第四层（语义推断）→ 兜底（日常收支）
```

| 层级 | 优先级 | 说明 | 示例 |
|------|--------|------|------|
| **第一层** | 最高 | 用户直接指令 | "打车50，记到旅游里" → 旅游 |
| **第二层** | 高 | 活跃项目（⭐标星） | 设置旅游为活跃项目后，所有消费优先记入旅游 |
| **第三层** | 中 | 记忆规则（历史学习） | 之前纠正过"星巴克→日常"，但活跃项目优先 |
| **第四层** | 低 | AI 语义推断 | "机票1000" → 推断为旅游（仅无活跃项目时） |
| **兜底** | - | 默认归入日常收支 | 无任何规则匹配时 |

---

## 二、活跃项目机制

### 2.1 什么是活跃项目？

活跃项目是用户**主动设置**的当前记账目标，代表用户当前的记账意图。

**核心特性：**
- 全局唯一：同一时间只能有一个活跃项目
- 绝对优先：设置后，所有消费（除非有直接指令）都优先记入活跃项目
- 临时覆盖：活跃项目优先级高于记忆规则

### 2.2 如何设置活跃项目？

| 入口 | 位置 | 操作 |
|------|------|------|
| **项目Tab** | 项目卡片右上角 ⭐ 按钮 | 点击设置/取消 |
| **AI对话页** | 顶部导航栏 ⭐ 按钮 | 下拉菜单快速切换 |

### 2.3 活跃项目 vs 置顶项目

| 功能 | 置顶项目 | 活跃项目 |
|------|----------|----------|
| 字段 | `isPinned` | `isActiveProject` |
| 用途 | 项目排序 | AI记账归属 |
| 数量 | 可多个 | 全局唯一 |
| 优先级 | 不影响AI | 第二层优先级 |

## 三、场景示例

### 3.1 设置活跃项目后的效果

```
用户设置"旅游"为活跃项目
用户说：买水10块

分析：
├── 第一层：无直接指令
├── 第二层：有活跃项目"旅游" ✅
├── 第三层：不执行（第二层已命中）
└── 第四层：不执行

结果：记入"旅游" ✅
```

### 3.2 活跃项目覆盖记忆规则

```
历史记忆：星巴克 → 日常收支（之前学的）
用户设置"旅游"为活跃项目
用户说：星巴克30

分析：
├── 第一层：无直接指令
├── 第二层：有活跃项目"旅游" ✅ （覆盖记忆规则）
├── 第三层：不执行（第二层已命中）
└── 第四层：不执行

结果：记入"旅游" ✅（不是日常收支）
```

### 3.3 直接指令覆盖活跃项目

```
用户设置"旅游"为活跃项目
用户说：星巴克30，记到日常收支

分析：
├── 第一层：有直接指令"记到日常收支" ✅
├── 第二层：不执行（第一层已命中）
├── 第三层：不执行
└── 第四层：不执行

结果：记入"日常收支" ✅（直接指令最高优先级）
```

### 3.4 无活跃项目时的行为

```
用户未设置活跃项目
历史记忆：星巴克 → 日常收支
用户说：星巴克30

分析：
├── 第一层：无直接指令
├── 第二层：无活跃项目
├── 第三层：有记忆规则"星巴克→日常收支" ✅
└── 第四层：不执行

结果：记入"日常收支" ✅
```

### 3.5 语义推断（仅无活跃项目时）

```
用户未设置活跃项目
存在"旅游"项目
用户说：携程订酒店500

分析：
├── 第一层：无直接指令
├── 第二层：无活跃项目
├── 第三层：无记忆规则
└── 第四层：AI语义推断"酒店→旅游" ✅

结果：记入"旅游" ✅
```

## 四、动态活跃项目推断

### 4.1 机制说明

除了用户手动设置，系统还会自动推断活跃项目：

```
最近5条交易中，如果有3条及以上属于同一个非"日常收支"项目
→ 该项目自动标记为 (近期高频活跃)
→ 后续消费优先记入该项目
```

### 4.2 示例

```
最近5条交易：
1. 机票1000 → 旅游
2. 酒店500 → 旅游
3. 景区门票200 → 旅游
4. 星巴克30 → 日常收支
5. 打车50 → 日常收支

分析：旅游出现3次（≥3），触发高频活跃
结果：后续消费优先记入"旅游"
```

## 五、冲突解决

### 5.1 多个活跃项目

**不会发生！** 活跃项目全局唯一，设置新活跃项目时自动取消旧的。

### 5.2 活跃项目 vs 直接指令

直接指令优先级最高，即使设置了活跃项目，用户明确指定项目时仍按指令执行。

### 8.2 关键代码

```swift
// AppStore.swift
func toggleActiveProject(_ project: Project) {
    if project.isActiveProject {
        project.isActiveProject = false
    } else {
        // 先取消所有其他项目的活跃状态
        let allProjects = (try? modelContext.fetch(FetchDescriptor<Project>())) ?? []
        for p in allProjects {
            p.isActiveProject = false
        }
        // 设置当前项目为活跃项目
        project.isActiveProject = true
    }
    save()
    refresh()
}
```

    var marker = ""
    if project.isActiveProject {
        marker = " (当前活跃项目⭐)"
    } else if highFrequencyProjects.contains(project.name) {
        marker = " (近期高频活跃)"
    }

}

## 九、使用流程

### 9.1 旅游记账场景

```
1. 出发前
   → 项目Tab → 点击"旅游"项目的星标 → 设为活跃项目

2. 旅游期间
   → 所有消费（吃饭、打车、买水）自动记入"旅游"
   → 即使有历史记忆"星巴克→日常"，也会记入旅游

3. 旅游结束
   → AI对话页 → 点击星标 → 取消活跃项目
   → 或项目Tab → 再次点击星标取消
   → 恢复正常记账逻辑
```

### 9.2 装修记账场景

```
1. 开始装修
   → 项目Tab → 点击"装修"项目的星标 → 设为活跃项目

2. 装修期间
   → 买建材、家具、家电等自动记入"装修"

3. 装修结束
   → 取消活跃项目
```

## 十、Bug 修复记录

### 10.1 活跃项目被记忆规则覆盖（已修复）

**发现时间**：2026-05-31

**问题描述**：

设置"创业"为活跃项目后，发送"买奶茶花了33"，AI 仍然将账单归入"日常收支"而非"创业"。

**日志关键片段**：

```
Available Projects:
- 日常收支
- 创业 (当前活跃项目⭐)

User Memory Rules:
- keyword: 奶茶, category: 饮品, project: 日常收支  ← 历史记忆

API Response: {"project_name": "日常收支"}  ← 错误结果
```

**根本原因**：

`parseTransaction`（自然语言输入处理方法）和 `parseOCRText`（截图识别处理方法）的 Prompt 规则不一致：

| 方法 | 4层优先级规则 |
|------|--------------|
| `parseOCRText` | ✅ 已有 |
| `parseTransaction` | ❌ 缺失（Bug 根源） |

由于"买奶茶花了33"走的是 `parseTransaction`，其 Prompt 没有活跃项目优先于记忆规则的说明，AI 直接采用了记忆规则中的 `project: 日常收支`。

**修复方案**：

在 `LLMService.swift` 的 `parseTransaction` 方法 systemPrompt 中补充完整的 **项目归属规则（第5条）**，明确规定：

> 如果 Context 中存在标记为 `(当前活跃项目⭐)` 的项目，无论 User Memory Rules 中记录了什么项目，都必须将 `project_name` 设为该活跃项目。

**修复文件**：`moneyfull_ios/Services/LLMService.swift` — `parseTransaction` 方法，新增规则5（项目归属优先级）。

**验证方法**：

1. 设置任意项目为活跃项目
2. 发送"买奶茶花了33"（已有记忆规则将奶茶指向"日常收支"）
3. 确认 API Response 中 `project_name` 返回活跃项目名称，而非"日常收支"
