# 钱小满 (Money Full) 数据埋点与运营分析方案

> **版本记录**
> - V1.0：基础功能埋点（引导、记账、项目、统计、设置）
> - V2.0：新增测评与画像埋点（2026-07-16）

## 一、 埋点目标与核心指标 (North Star Metrics)

作为一款主打「项目制」和「治愈系」的本地记账 App，我们的运营目标不是榨取用户隐私，而是**验证核心功能（项目制）的接受度**，以及**提升用户的记账留存率**。

**核心监控指标：**
1. **激活率**：下载 App 后，完成新手引导并记下第一笔账的用户占比。
2. **核心特色渗透率**：除了默认的「日常收支」，主动新建过至少 1 个自定义项目（如旅游、装修）的用户占比。
3. **留存率（次日/七日/次月）**：记账产品的生命线，观察小满的治愈文案是否提升了留存。
4. **记账频次**：活跃用户平均每天/每周记录的账单笔数。

## 二、 用户标识与基础指标 (User ID & DAU/Retention)

在没有任何自定义埋点代码的情况下，只要接入了数据 SDK（如友盟、Firebase），你就能自动获得以下三个最核心的运营数据：

### 1. 独立用户 ID (Device ID)
因为钱小满 v1.0 是纯本地 App，**没有注册/登录功能**（没有手机号或微信号），所以 SDK 会自动为每台下载了 App 的手机生成一个独一无二的**「设备 ID (Device ID / IDFV)」**。
- **对统计后台而言**：1 台设备 = 1 个独立用户 (Unique Visitor, UV)。
- **后续扩展**：如果未来版本加入了账号登录功能，我们可以调用 SDK 的 `setUserId("手机号/微信ID")`，把这个设备 ID 和真实的账号 ID 绑定起来，实现跨设备的数据互通。

### 2. 每日活跃用户 (DAU - Daily Active Users)
- **无需手动埋点**：SDK 会自动监听 App 的「启动」和「退到后台」事件。
- **你能看到什么**：在数据后台，你可以直接按日期（如 4月12日）看到一条折线图，显示当天有多少个独立用户（设备）打开了 App。你还可以看 WAU（周活）和 MAU（月活）。

### 3. 用户留存率 (Retention)
- **无需手动埋点**：后台会自动根据用户的「首次启动日期」和「后续启动日期」计算留存。
- **你能看到什么**：经典的留存漏斗表。例如：4月1日有 100 个新用户下载并打开了 App；4月2日这批人里有 40 个再次打开了 App，那么 **次日留存率就是 40%**；4月8日还有 15 个人打开，**7日留存率就是 15%**。

## 三、 隐私与合规原则（极其重要）

由于我们在 App Store 宣传了「完全基于本地化存储，纯净安全」，在引入埋点 SDK（如 友盟、Firebase Analytics、神策等）时，必须严格遵守以下底线：
- **绝不上报具体金额**：将金额转化为区间（如 `0-50`, `50-200`, `200-1000`, `1000+`）进行上报。
- **绝不上报用户备注**：备注涉及绝对隐私，坚决不上报。
- **脱敏处理**：只上报行为事件（点击了什么按钮、进入了什么页面）和分类名称。
- **合规弹窗**：在首次启动时，必须有隐私协议同意弹窗，用户同意后才初始化 SDK。

## 三、 核心埋点事件设计 (Event Tracking Plan)

事件命名规范建议采用：`模块_动作_对象`（如 `onboarding_view_page`）。

### 3.1 新手引导与激活 (Onboarding)
用于分析新手引导的流失率，看看用户在哪一页不耐烦了。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `onboarding_view_page` | 浏览引导页 | 引导页曝光时 | `page_index` (0, 1, 2) |
| `onboarding_click_skip` | 点击跳过引导 | 点击右上角跳过按钮时 | `current_page_index` (当前停留的页码) |
| `onboarding_complete` | 完成引导 | 点击最后一页的「开始记账」时 | 无 |

### 3.2 核心动作：记一笔 (Add Record)
分析用户的记账习惯，这是 App 最核心的数据。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `record_click_add` | 点击记一笔入口 | 点击底部「+」号时 | `source` (dashboard/project_detail) |
| `record_submit_success` | 记账成功 | 点击「确认」并成功保存时 | `type` (expense/income)<br>`category` (餐饮/交通等)<br>`is_custom_project` (true/false，是否记在自定义项目下)<br>`amount_level` (金额区间，如 level_1_under100) |
| `record_cancel` | 取消记账 | 点击左上角「X」关闭弹窗时 | `has_input_amount` (true/false，是否输入了金额但没保存) |

### 3.3 核心特色：项目管理 (Project Management)
验证「项目制记账」这个核心卖点是否立得住。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `project_click_new` | 点击新建项目 | 点击项目中心的「新建项目」时 | 无 |
| `project_create_success` | 成功创建项目 | 提交新建项目表单时 | `has_budget` (true/false，是否设置了预算)<br>`icon_selected` (选了哪个图标) |
| `project_view_detail` | 查看项目详情 | 点击项目卡片进入详情页时 | `project_status` (active/archived) |
| `project_archive` | 归档项目 | （未来功能预留）用户归档项目时 | `project_duration_days` (项目持续了多少天) |

### 3.4 财务统计与情绪价值 (Analytics & Capybara)
分析用户对数据报表和「豚言豚语」的关注度。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `analytics_view_page` | 浏览统计页 | 切换到底部「统计」Tab时 | `has_data` (true/false，当月是否有数据) |
| `analytics_change_month` | 切换统计月份 | 在统计页选择其他月份时 | 无 |
| `analytics_click_report` | 点击深度报告 | 点击深绿卡片的「立即生成深度报告」时 | 无 (用于评估后续是否要开发 AI 报告付费功能) |

### 3.5 设置与偏好 (Profile & Settings)

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `profile_change_theme` | 切换外观主题 | 在个人中心切换主题时 | `theme_selected` (light/dark/system) |

### 3.6 用户测评与画像 (Assessment & Persona) - V2.0 新增

验证测评流程的完成率，以及将用户画像与设备 ID 绑定，用于后续的用户分群分析和个性化功能验证。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `assessment_completed` | 测评完成 | 用户完成 4 道测评题后 | `habit` (habit_none/habit_lapsed/habit_sometimes/habit_daily/habit_consistent)<br>`method` (method_none/method_payment_app/method_excel/method_other_app/method_handwrite)<br>`income` (income_salary/income_freelance/income_multi/income_student)<br>`jtbd` (jtbd_ease/jtbd_insight/jtbd_roi/jtbd_budget/jtbd_import)<br>`health_score` (0~100，健康分) |
| `persona_generated` | 画像生成 | 系统根据选项计算出画像后 | `persona_type` (persona_earner/persona_efficiency/persona_moonlight/persona_datadriven/persona_steady)<br>`persona_name` (项目创收者/效率优先者/月光规划师/数据控进阶者/稳健积累者)<br>`persona_letter` (A/B/C/D/E)<br>`health_score` (0~100)<br>`habit` / `method` / `income` / `jtbd` (同上，便于交叉查询) |

**分析价值**：
1. **用户画像分布**：了解哪类用户最多，指导功能优先级
2. **健康分分布**：评估用户整体财务健康状况
3. **画像与留存关联**：分析不同画像用户的留存差异
4. **画像与付费关联**：验证哪类画像用户更愿意付费

### 3.7 订阅与付费 (Subscription & Payment) - V2.0 新增

监控订阅转化漏斗，优化付费墙展示策略。

| 事件 ID | 事件名称 | 触发时机 | 核心参数 (Parameters) |
| :--- | :--- | :--- | :--- |
| `paywall_viewed` | 打开订阅页 | 进入 PaywallView 时 | `source` (profile/home) |
| `paywall_plan_selected` | 选择订阅方案 | 点击月卡/年卡/终身卡时 | `plan_type` (monthly/annual/lifetime)<br>`price` (方案价格) |
| `paywall_cta_tapped` | 点击开通按钮 | 点击"开通/升级"按钮时 | `plan_type`<br>`is_upgrade` (true/false) |
| `paywall_purchase_success` | 购买成功 | StoreKit 交易完成时 | `product_id`<br>`plan_type`<br>`price` |
| `paywall_purchase_failed` | 购买失败 | StoreKit 交易失败时 | `product_id`<br>`error_reason` |
| `paywall_letter_viewed` | 查看付费说明 | 点击"关于会员付费上线的说明"时 | `source` (paywall) |

**分析价值**：
1. **订阅转化漏斗**：paywall_viewed → paywall_plan_selected → paywall_cta_tapped → paywall_purchase_success
2. **方案偏好**：了解用户更倾向月卡/年卡/终身卡
3. **付费说明点击率**：评估用户对付费政策的关注度

## 四、 用户属性设置 (User Properties)

除了单次事件，我们还需要给每个用户打上「属性标签」，每次上报事件时自动携带，方便进行交叉分析（例如：建了多个项目的用户，留存率是不是更高？）。

| 属性名 (Property) | 说明 | 更新时机 |
| :--- | :--- | :--- |
| `total_projects_count` | 累计创建的项目总数 | 每次新建项目后更新 (+1) |
| `total_transactions_count`| 累计记账总笔数 | 每次记账成功后更新 (+1) |
| `days_since_install` | 安装至今的天数 | 每日首次启动时计算更新 |
| `current_theme` | 当前使用的主题 | 切换主题时更新 |
| `persona_type` | 用户画像类型 | 测评完成后更新 |
| `persona_letter` | 画像字母标识 | 测评完成后更新 |
| `health_score` | 财务健康分 | 测评完成后更新 |
| `income_type` | 收入来源类型 | 测评完成后更新 |
| `jtbd_choice` | JTBD 意图选择 | 测评完成后更新 |
| `has_completed_assessment` | 是否完成测评 | 测评完成后设为 true |

## 五、 运营分析场景举例 (如何使用这些数据？)

1. **功能渗透分析**：
   - 公式：`触发 project_create_success 的独立用户数` / `总活跃用户数`。
   - 目的：如果这个比例低于 10%，说明绝大多数人还是把钱小满当普通流水账在用，我们需要在首页增加更强的「新建项目」引导，或者优化新建流程。
2. **商业化潜力测试**：
   - 观察 `analytics_click_report` (点击生成深度报告) 的触发次数。
   - 目的：这目前是一个占位按钮。如果点击率极高，说明用户对深度财务分析有强烈需求，下个版本就可以顺势推出「AI 财务诊断」的内购高级版（Pro 功能）。
3. **流失节点排查**：
   - 漏斗：`record_click_add` -> `record_submit_success`。
   - 目的：如果用户点了「+」号，但大量触发了 `record_cancel`，说明记账界面的交互可能存在阻力，需要进一步简化。
4. **用户画像与留存关联分析**（V2.0 新增）：
   - 按 `persona_type` 分组，对比不同画像用户的次日/7日/30日留存率。
   - 目的：验证哪类用户对产品粘性最高，指导获客渠道和功能优化方向。
5. **画像与付费转化分析**（V2.0 新增）：
   - 按 `persona_type` 分组，对比不同画像用户的付费转化率。
   - 目的：了解哪类用户更愿意付费，优化付费墙展示策略和定价方案。
6. **健康分分布分析**（V2.0 新增）：
   - 统计 `health_score` 的分布区间（0~40 / 40~60 / 60~80 / 80~100）。
   - 目的：评估用户整体财务健康状况，验证测评算法的合理性。
