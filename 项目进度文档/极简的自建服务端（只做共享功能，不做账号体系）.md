# 极简共享记账服务 — 详细方案

**文档版本**：v1.1（补充数据库命名规范、生态打通预留、单人数据备份说明）
**创建日期**：2026-09-04
**定位**：在不做账号体系的前提下，快速验证"多人共享记账"需求的最小可行方案

## 总体架构

```
┌─────────────────────────────────────────────────────────┐
│  iOS App                                                │
│  ┌──────────────────┐    ┌──────────────────────────┐  │
│  │  单人模式（现有）   │    │  共享项目模式（新增）       │  │
│  │  SwiftData+iCloud │    │  直接读写共享服务器         │  │
│  └──────────────────┘    └──────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
                                    ↕ HTTP
┌─────────────────────────────────────────────────────────┐
│  极简共享服务（Node.js）                                  │
│  不需要账号体系，invite_code 作为唯一访问凭证              │
└─────────────────────────────────────────────────────────┘
                                    ↕ SQL
┌─────────────────────────────────────────────────────────┐
│  MySQL — originapex_db（公司统一数据库实例）               │
│  本阶段：3 张 mf_shared_* 表                             │
└─────────────────────────────────────────────────────────┘
```

**关键设计原则**：

- 单人记账 = SwiftData + iCloud（现有代码零改动）
- 共享记账 = 数据只在服务器，不与本地 SwiftData 混用，隔离清晰
- `invite_code` 是唯一的访问控制，不需要 JWT、不需要账号

## 一、数据库命名规范（与生态长期规划对齐）

> 这是整个产品矩阵共用一个 MySQL 实例的命名策略，现在就按这个规范建表，未来扩展零成本。

```
数据库实例：originapex_db（公司名 OriginApex，统一实例）

表前缀规范：
├── mf_*          钱小满（MoneyFull）的专属表
├── lc_*          人生教练（LifeCoach）的专属表（后续新增）
├── users         共用身份表（账号体系上线后建）
├── portrait_*    用户画像层（第二步后建）
└── agent_*       Agent 智能层（第三步后建）

本阶段建的 3 张表：
├── mf_shared_projects          → 将来升级为 mf_projects
├── mf_shared_project_members   → 将来升级为 mf_project_members
└── mf_shared_transactions      → 将来升级为 mf_transactions
```

> **为什么表名加 `shared_` 中间层？**
> 为了和将来带账号体系的正式表明确区分，避免混淆。
> 升级时重命名即可，不影响已存在的数据。

## 二、数据库设计（3 张表）

```sql
-- =============================================
-- 共享项目表
-- =============================================
CREATE TABLE mf_shared_projects (
    id                   VARCHAR(36) PRIMARY KEY,       -- 客户端生成的 UUID
    invite_code          VARCHAR(8) NOT NULL UNIQUE,    -- 邀请码，大写字母+数字，如 "AB3X7K"
    name                 VARCHAR(100) NOT NULL,
    created_by_device_id VARCHAR(100) NOT NULL,         -- 创建者的设备号
    is_deleted           TINYINT(1) DEFAULT 0,
    created_at           TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_invite (invite_code)
);

-- =============================================
-- 共享项目成员表（加入时写入，记录昵称）
-- =============================================
CREATE TABLE mf_shared_project_members (
    id               BIGINT AUTO_INCREMENT PRIMARY KEY,
    project_id       VARCHAR(36) NOT NULL,
    device_id        VARCHAR(100) NOT NULL,
    participant_name VARCHAR(50) NOT NULL,              -- 成员自己填的昵称（如"阿杰"）
    future_user_id   BIGINT NULL,                       -- 【升级预留】账号体系上线后回填为 user_id
    joined_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_project_device (project_id, device_id),
    INDEX idx_project (project_id)
);

-- =============================================
-- 共享流水表（核心数据）
-- =============================================
CREATE TABLE mf_shared_transactions (
    id               VARCHAR(36) PRIMARY KEY,           -- 客户端生成的 UUID（保证离线重试幂等）
    project_id       VARCHAR(36) NOT NULL,
    device_id        VARCHAR(100) NOT NULL,             -- 是哪台设备记的
    participant_name VARCHAR(50),                       -- 冗余存储，方便展示（加入时的昵称快照）
    future_user_id   BIGINT NULL,                       -- 【升级预留】账号体系上线后回填为 user_id
    amount           DECIMAL(12, 2) NOT NULL,
    category         VARCHAR(50),
    note             TEXT,
    transaction_at   TIMESTAMP NOT NULL,               -- 用户填的时间
    is_deleted       TINYINT(1) DEFAULT 0,
    server_updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_project_sync  (project_id, server_updated_at),  -- 增量同步核心索引
    INDEX idx_project_active (project_id, is_deleted)
);
```

> **`future_user_id` 字段说明**：
> 账号体系上线后，通过 `device_id` → `user_app_memberships.device_id` 关联查到 `user_id`，
> 一条 UPDATE 语句批量回填，再将列重命名为 `user_id`，完成升级。
> 现在预留此列，升级时无需 `ALTER TABLE ADD COLUMN`（减少线上风险）。

## 三、API 设计（6 个接口）

### 3.1 创建共享项目

```
POST /shared-projects

Request Body:
{
  "id": "uuid-client-generated",   // 客户端生成，保证幂等
  "name": "我们的家庭账本",
  "createdByDeviceId": "ABC123",
  "creatorName": "阿杰"            // 创建者的昵称
}

Response 201:
{
  "projectId": "uuid-...",
  "inviteCode": "AB3X7K",          // 服务端生成，6位大写字母数字
  "name": "我们的家庭账本"
}
```

### 3.2 通过邀请码加入项目

```
POST /shared-projects/join

Request Body:
{
  "inviteCode": "AB3X7K",
  "deviceId": "XYZ456",
  "participantName": "小明"        // 加入时填的昵称
}

Response 200:
{
  "projectId": "uuid-...",
  "name": "我们的家庭账本",
  "members": [
    { "participantName": "阿杰", "joinedAt": "2026-09-01T..." },
    { "participantName": "小明", "joinedAt": "2026-09-04T..." }
  ]
}

Response 404: { "error": "邀请码不存在或已失效" }
```

### 3.3 拉取流水（增量同步）

```
GET /shared-projects/:inviteCode/transactions?since=2026-09-01T00:00:00Z&deviceId=ABC123

// since 参数：上次同步时间，首次传 0 或不传，拉全量
// 返回包含 is_deleted=1 的记录（客户端据此本地删除）

Response 200:
{
  "transactions": [
    {
      "id": "uuid-...",
      "deviceId": "XYZ456",
      "participantName": "小明",
      "amount": 38.50,
      "category": "餐饮",
      "note": "午饭",
      "transactionAt": "2026-09-04T12:30:00Z",
      "isDeleted": 0,
      "serverUpdatedAt": "2026-09-04T12:30:05Z"
    }
  ],
  "serverTime": "2026-09-04T12:31:00Z"  // 客户端存下来作为下次 since 的值
}
```

> ⚠️ `since` 用服务端返回的 `serverTime` 而不是客户端时钟，防止时区/时钟偏差导致漏数据

### 3.4 写入流水（支持批量）

```
POST /shared-projects/:inviteCode/transactions

Request Body:
{
  "deviceId": "ABC123",
  "transactions": [
    {
      "id": "uuid-client-gen",    // 客户端生成，实现幂等写入
      "amount": 128.00,
      "category": "购物",
      "note": "超市",
      "transactionAt": "2026-09-04T18:00:00Z"
    }
  ]
}

Response 200:
{
  "saved": ["uuid-client-gen"],
  "serverTime": "2026-09-04T18:00:05Z"
}
```

> 服务端用 `INSERT ... ON DUPLICATE KEY UPDATE` 保证幂等，网络重试不会产生重复数据

### 3.5 删除流水（逻辑删除）

```
DELETE /shared-projects/:inviteCode/transactions/:transactionId

Request Body:
{
  "deviceId": "ABC123"    // 校验是否是自己记的，防止误删别人的账
}

Response 200: { "ok": true }
Response 403: { "error": "只能删除自己记录的流水" }
```

### 3.6 退出/解散共享项目

```
DELETE /shared-projects/:inviteCode/members/:deviceId

// 创建者退出 = 解散（mf_shared_projects.is_deleted = 1，所有人下次拉取时感知到）
// 普通成员退出 = 仅删除自己在成员表的记录
```

**核心代码片段（邀请码生成，保证唯一）**：

```javascript
// utils/inviteCode.js
const CHARS = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'; // 去掉易混淆的 0/O/1/I

async function generateUniqueCode(db) {
  for (let attempt = 0; attempt < 10; attempt++) {
    let code = '';
    for (let i = 0; i < 6; i++) {
      code += CHARS[Math.floor(Math.random() * CHARS.length)];
    }
    const [rows] = await db.execute(
      'SELECT id FROM mf_shared_projects WHERE invite_code = ?', [code]
    );
    if (rows.length === 0) return code; // 没有碰撞，直接用
  }
  throw new Error('邀请码生成失败，请重试');
}
```

**幂等写入的 SQL 模式**：

```sql
INSERT INTO mf_shared_transactions
  (id, project_id, device_id, participant_name, amount, category, note, transaction_at)
VALUES
  (?, ?, ?, ?, ?, ?, ?, ?)
ON DUPLICATE KEY UPDATE
  amount         = VALUES(amount),
  category       = VALUES(category),
  note           = VALUES(note),
  transaction_at = VALUES(transaction_at);
  -- ⚠️ server_updated_at 由 ON UPDATE CURRENT_TIMESTAMP 自动更新
```

## 六、安全与限流

| 风险 | 处理方式 |
|------|---------|
| 邀请码暴力猜测 | 同一 IP 每分钟最多尝试 5 次 join；失败 3 次后 IP 级冷却 60s |
| 恶意大量写入 | 同一 device_id 每分钟最多写入 50 条 |
| 删别人的账 | DELETE 接口校验 device_id 必须是记账人 |
| 邀请码泄露 | 支持创建者"更换邀请码"接口（旧码失效），PRD 可后续加 |
| 服务端宕机 | 共享功能不可用，不影响单人模式（SwiftData 照常工作） |

## 七、升级到完整账号体系的路径

### 7.1 表结构的演进

本阶段建的 3 张表，与完整账号体系 PRD 的正式表**直接对应**：

| 当前表（极简共享阶段） | 升级后（完整 PRD） | 升级操作 |
|---|---|---|
| `mf_shared_projects` | `mf_projects` | 重命名 + 加 `created_by_user_id` 列 |
| `mf_shared_transactions` | `mf_transactions` | 重命名 + `future_user_id` 列改名为 `created_by_user_id` |
| `mf_shared_project_members` | `mf_project_members` | 重命名 + `future_user_id` 列改名为 `user_id` |

**升级迁移 SQL（核心两步）**：

```sql
-- 第一步：通过 device_id 关联 user_id，回填 future_user_id
UPDATE mf_shared_transactions t
JOIN user_app_memberships m ON t.device_id = m.device_id AND m.app_id = 'moneyfull'
SET t.future_user_id = m.user_id;

-- 第二步：重命名列（各表同理）
ALTER TABLE mf_shared_transactions
  RENAME COLUMN future_user_id TO created_by_user_id;

-- 之后重命名表（不影响数据）
RENAME TABLE mf_shared_projects TO mf_projects;
RENAME TABLE mf_shared_transactions TO mf_transactions;
RENAME TABLE mf_shared_project_members TO mf_project_members;
```

一次 migration + 后端接口改为 JWT 鉴权 = 升级完毕，**现有数据不丢、不重写**。

## 八、关于单人数据备份（不合并进本方案）

**问**：能不能同时把单人用户的 iCloud 数据也上传到 `originapex_db`，做双写备份？

**答**：不建议在本阶段合并，原因如下：

| 问题 | 说明 |
|------|------|
| 没有账号，备份价值有限 | 单人数据用 `device_id` 标记，换手机后 `device_id` 变了，服务端数据找不回来，等于白备份 |
| 语义混淆 | 单人私有数据和多人共享数据性质不同，混在同一批表里会导致查询逻辑复杂 |
| 已有更好的方案 | 账号体系 PRD（`账号体系与数据云化PRD.md`）已经设计了完整的 `/sync/migrate` 迁移接口，用户登录时一次性把历史数据上传，这才是正确的"备份到服务器"的时机 |

**结论**：单人数据备份等账号体系上线后，通过 PRD 里的 `/sync/migrate` 接口完成，现阶段不做，不留技术债。
