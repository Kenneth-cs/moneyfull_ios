**问题现象**：App 越用越卡，上下滑动掉帧；有时滑动第一下没反应，需要划第二次

> **v1.1 更新内容**：第一批（首页 / 全部账单页 / 项目卡片 / 手势）已完成。在为第二批做排查时新增三项发现：

## 一、结论速览

| 现象 | 根因 | 是否与数据量相关 |
|------|------|-----------------|
| 越用越卡、滚动掉帧 | 统计值写成 computed property，**每次 view body 重算都做一次全表扫描**，且同一个值在一次 body 里被重复算 3~7 遍 | ✅ 成本随笔数线性增长 |
| 滑动第一下没反应 | 每行账单挂了自定义 `DragGesture`，与 ScrollView 的 pan 手势抢触摸 | ❌ 与数据量无关，独立问题 |
| 卡顿被同步放大 | CloudKit / 任意写入 → `objectsDidChange` → `AppStore.refresh()` 无条件全量刷新 → 全屏重绘 → 上述全表扫描重跑 | ✅ |
| *(v1.1 新增)* 统计页数字有时不更新 | 刷新信号选错，不是缓存的锅 —— 详见 P0-6 | ❌ 与数据量无关 |

**不是 iCloud 实时同步本身的问题**。同步只是触发器，真正的成本在客户端渲染路径。

**修复进度**：P0-1 / P0-2 / P0-3 / P0-5 已在第一批修复；P0-4 / P0-6 / P1-1 属第二批范围。

## 二、根因诊断（问题清单）

### P0-1 · 首页每次重绘 = 3 次全表扫描 + 1 次 count 查询　`✅ 第一批已修复`

**位置**：`moneyfull_ios/Views/DashboardView.swift:40-48`

```swift
// 根据选中维度获取统计数据（store.refresh() 有 500ms 防抖，不会在滚动中触发，直接计算保证实时同步）
private var currentStats: (expense: Double, income: Double, saving: Double) {
    store.stats(for: selectedPeriod)
}
```

`currentStats` 是无缓存的 computed property，在 body 中被访问 **3 次**：

- `DashboardView.swift:92` → `currentStats.expense`
- `DashboardView.swift:100` → `currentStats.income`
- `DashboardView.swift:101` → `currentStats.saving`

每次访问都完整跑一遍 `AppStore.stats(for:)`（`Models/AppStore.swift:257-281`）：

```swift
let descriptor = FetchDescriptor<Transaction>(sortBy: [SortDescriptor(\.date, order: .reverse)])
let allTxs = (try? modelContext.fetch(descriptor)) ?? []          // 全表 fetch + 全量排序
let txs = period == .all ? allTxs : allTxs.filter { $0.date >= startDate }  // 内存 filter
let exp = txs.filter { $0.type == .expense }.reduce(0) { ... }
let inc = txs.filter { $0.type == .income  }.reduce(0) { ... }
```

**两个独立问题**：

1. 没有缓存，一次 body 算 3 遍。
2. 即使只看"本月"，也是**先把全部账单查出来并排序**再在内存里 filter，没有用 `#Predicate` 下推到数据库。所以"本月"的成本 = "累计"的成本 = O(总笔数)。

**原注释的假设不成立**：body 重算的触发源远不止 `refresh()` —— 切 tab、任何 `@State` 变化、sheet 开关、系统 trait 变化、父视图重绘都会触发。

**额外问题**：`DashboardView.swift:315-317`

```swift
.onChange(of: store.fetchTotalTransactionCount()) {
    checkExportBannerIfNeeded()
}
```

`onChange(of:)` 的 `of:` 表达式在**每次 body 求值时**都会被计算 → 每次重绘多打一次数据库 count 查询。

**同类写法**：
- `Views/ProfileView.swift:28` → `private var totalTxCount: Int { store.fetchTotalTransactionCount() }`
- `Views/ProjectDetailView.swift:539` → `.onChange(of: project.transactions?.count)`（更贵，会把整个关系 fault 进来）

所有统计都串在无缓存的 `filteredTransactions` 上（`:45-109`），而它每次都重新 `store.fetchAllTransactions()`：

|--------|------|----------------|

### P0-3 · 项目卡片每张遍历两遍自己的全部账单　`✅ 第一批已修复`

**位置**：`moneyfull_ios/Views/DashboardView.swift:450-452`、`Views/ProjectsView.swift:167-169`

### P0-4 · 经营看板：单次渲染 48 处全量遍历　`⏳ 第二批`

**位置**：`moneyfull_ios/Views/ProjectDashboardView.swift`

`Project` 上有 30+ 个"每次访问都重新遍历 `transactions`"的计算属性（`Models.swift:239-390`）。`ProjectDashboardView` 里这类访问共 **48 处**，典型的：

```swift
// :966-971 —— 光这一段就是 6 次全量遍历
let total = project.directCost + project.fixedCostMonthly + project.personalCost
    direct:   (project.directCost      / total) * 100,
    fixed:    (project.fixedCostMonthly / total) * 100,
    personal: (project.personalCost    / total) * 100

// :1018-1022 —— 5 次，且写在 GeometryReader 闭包里，布局阶段会被反复求值
let directCostWidth   = geometry.size.width * (project.directCost      / maxValue)
let fixedCostWidth    = geometry.size.width * (project.fixedCostMonthly / maxValue)
let personalCostWidth = geometry.size.width * (project.personalCost    / maxValue)
let taxWidth          = geometry.size.width * (project.taxReserve      / maxValue)
```

#### 补充发现 A：计算属性会**级联放大**，48 处远不止 48 次遍历

v1.0 里按"48 处访问 = 48 次遍历"估算，实际更糟。`Project` 上的计算属性彼此嵌套调用，一次属性访问会展开成多次全量遍历：

```
project.operatingNetProfit
  → grossProfit          → monthlyIncome（遍历）+ directCost（遍历）
  → fixedCostMonthly     → 遍历 fixedCosts
  → taxReserve           → grossProfit（又把上面整条重算一遍）
```

也就是说读一个 `operatingNetProfit`，底层会把 `transactions` 扫 4~6 遍。经营看板一次渲染的真实遍历次数是**百量级**，不是 48。`ProjectDetailView.earningEntryCard`（`:764-789`）虽然只有 6 处访问，展开后同样约 25 次遍历 —— 这解释了为什么**项目详情页还没点进看板就已经卡了**。

#### 补充发现 B：`ProjectEarningView.swift`（548 行）是死代码

排查时确认：`ProjectDetailView` 里 `showEarningDashboard` 这个开关**没有任何地方会把它置为 true**，对应的 `fullScreenCover`（`:511-517`）永远不会弹出，用户从来打不开这个页面。经营看板的真实入口是 `ProjectDashboardView`。

所以 v1.0 里"`ProjectEarningView` 有同类问题（18 处），需要一起改造"这条**作废** —— 直接删文件即可，不需要优化。这也意味着第二批的实际工作量比预估小一档。

#### 补充发现 C：顺带发现一个数据正确性 bug

`ProjectDashboardView.calculateAmountForPeriod`（`:304-337`）在计算区间时，`endDate` 被写死成"起点 + 1 个月"，没有跟随传入的周期。结果是**选季度和选年度时，图表取的仍然是一个月的数据**。属于既有 bug，改造时一并修掉。

### P0-5 · 滑动第一下没反应：手势冲突　`✅ 第一批已修复`

**位置**：`moneyfull_ios/Components/CommonViews.swift:466-487`

```swift
content
    .offset(x: offset)
    .gesture(
        DragGesture(minimumDistance: 20)
            .onChanged { value in ... }
    )
```

`.gesture()` 挂在 ScrollView 内部的 cell 上，会与 ScrollView 的 pan 手势竞争。用户手指稍微斜一点，`DragGesture` 就可能先认领触摸，ScrollView 这一下就不滚 —— 表现即"划了一下没反应"。

**注意**：SwiftUI 的 `.gesture` 一旦认领触摸，无法中途把控制权还给 ScrollView，所以"在 onChanged 里判断方向再放弃"这种补丁无效。

> 主线程被阻塞 300ms 时用户体感也是"没反应"，两个原因可能叠加。修完 P0-1~P0-4 后需要重新评估此项的实际影响。

### P0-6 · 统计页：**数字漏更新**（正确性 bug）+ 重算本身偏慢　`⏳ 第二批`　*(v1.1 新增)*

**位置**：`moneyfull_ios/Views/AnalyticsView.swift`

这是第二批排查中新增的一项。统计页有两个独立的问题，一个关乎对错，一个关乎快慢。

**问题一（正确性，优先级更高）：刷新信号选错了，四种常见场景数字不更新。**

```swift
// :385-386
.onChange(of: store.recentTransactions.count) { _, _ in reloadFromStore() }
.onChange(of: store.monthlyExpense)           { _, _ in reloadFromStore() }
```

注释里写的是"覆盖所有 CRUD 场景"，但这两个信号都有盲区：

- `recentTransactions` 只取最近 50 条，**补记一笔上个月的账**排不进前 50，count 不变；
- 即使排进去了，是"新增一条 + 挤掉最老一条"，count 仍然是 50，**不变**；
- `monthlyExpense` 只统计本月**支出**，记一笔**收入**它不动；
- 只改分类不改金额，它也不动。

结论：**新增收入 / 补记往月账单 / 修改分类 / 删除往月账单**这四种情况下，用户回到统计页会看到旧数字。这正是当初"怕缓存不同步"要极力避免的现象 —— 讽刺的是，唯一真出现这个问题的页面，恰恰是缓存做得最规范的那一个。根因不在缓存策略，在**刷新信号的选取**。

第一批已经在 `AppStore` 引入了 `dataVersion`，改用它驱动即可根治。

**问题二（性能）：重算路径有三处可优化。**

| 位置 | 问题 | 影响 |
|------|------|------|
| `:164` | `Calendar.current` 写在循环体内，每行账单都新建一个 Calendar | Calendar 构造不便宜，N 次白造 |
| `:95` | 月份过滤用 `calendar.isDate(_:equalTo:toGranularity:)` 逐行判断 | 比直接比较 `Date` 区间慢一个量级 |
| `:214-265` | `computeTrendData()` 对每个时间桶重新遍历一次全部账单 | O(N × 桶数)，年视图 12 桶即 12 遍全表 |

这三项都是纯算法改写，不改变输出结果，可以对拍验证。

### P1-1 · `refresh()` 无条件全量刷新，触发全屏重绘

**位置**：`moneyfull_ios/Models/AppStore.swift:70-121`

```swift
NotificationCenter.default.addObserver(forName: .NSManagedObjectContextObjectsDidChange, ...) {
    self?.triggerDebouncedRefresh()        // 500ms 防抖
}

func refresh() {
    fetchProjects()            // 赋值 activeProjects / archivedProjects
    fetchRecentTransactions()  // 赋值 recentTransactions
    fetchCategories()          // 赋值 categories（内部可能触发 save()）
    fetchAppNotices()          // 赋值 appNotices
    calcMonthlyStats()         // 赋值 monthlyExpense / monthlyIncome / monthlySaving
}
```

**三个问题**：

1. `@Published` **没有相等性判断** —— 即使数据一个字节没变，赋值也会触发 `objectWillChange`。
2. `@EnvironmentObject` 订阅的是 `objectWillChange`（不是单个属性），所以**任意一个 `@Published` 变化都会让所有持有 `store` 的 view 整体重绘**。`MainTabView` 里 5 个 tab 全部常驻并持有 `store`。
3. 改了一个分类，`recentTransactions` 也会被重新赋值 → 首页全量重绘 → P0-1 的三次全表扫描重跑。

## 三、核心设计原则：缓存 ≠ 不实时

> 这一节回答"为什么当初不敢缓存"。

### 现在这种写法，并没有带来它承诺的实时性

SwiftUI **不是**每秒 60 次重跑 body 的，它只在**被追踪的依赖变化**时重跑。而 `store.stats(for:)` 直接读 `modelContext`，SwiftUI 追踪不到这个依赖。

那为什么记完账回首页数字是新的？走的是这条链路：

```
addTransaction() → save() → refresh() → 给 @Published 赋值
      ↓
AppStore.objectWillChange 触发
      ↓
所有 @EnvironmentObject var store 的 view 整体重绘
      ↓
重绘时"顺带"把 stats(for:) 又算了一遍
```

**真正保证实时性的是 `refresh()` 里给 `@Published` 赋值那一步**，不是"在 body 里算"这个动作。body 里算只是搭了个顺风车。

### 推论

只要在 `refresh()` 执行的那个位置把统计值算好存起来，**实时性完全一致，一帧都不会晚**。"用户以为软件 bug 了"的风险在正确的缓存方案下不存在 —— 因为缓存失效时机 == 当前触发重绘的时机。

### 成本对比

| | 记一笔账 | body 重绘 |
|---|---|---|
| 频率 | 每天几次~几十次 | 每次滚动 / 切 tab / 开关 sheet / trait 变化…… 每天上万次 |
| 现在在哪算 | 算（refresh 里） | **也算，且一次算 3~7 遍** |

用"每天 20 次事件"的正确性，换"每天上万次渲染"的开销，不划算。

### 参考实现：`AnalyticsView` 的**渲染路径**是正确范式

`Views/AnalyticsView.swift:51-78` 已经完成过一轮优化，这套结构可直接照抄：

```swift
// MARK: - 缓存计算结果（避免 body 每次重渲时重复执行耗时操作）
@State private var _filteredTransactions: [Transaction] = []
@State private var _donutSegments: [...] = []
// ...

// MARK: - 计算属性代理（body 直接读缓存，零计算开销）
private var filteredTransactions: [Transaction] { _filteredTransactions }
private var donutSegments: [...] { _donutSegments }

// MARK: - 核心统计刷新（仅在过滤条件变化时调用，不在 body 里计算）
private func updateFilteredData() { ... }
```

> **v1.1 更正**：值得照抄的是上面这个"body 只读缓存"的**结构**。但 `AnalyticsView` 自己有两处不要抄：
> 一是**它决定何时重算的信号选错了**，会漏刷（详见 P0-6 问题一），刷新信号请统一用 `dataVersion`；
> 二是 `updateFilteredData()` 内部的算法本身偏慢（详见 P0-6 问题二）。
>
> 换句话说，"什么时候算"和"算得快不快"是两件独立的事，缓存范式只解决了第三件事——"别在 body 里算"。

## 四、数据分层策略（哪些实时、哪些异步）

| 层级 | 内容 | 时效要求 | 实现方式 |
|------|------|---------|---------|
| **L1 · 同步实时** | 首页本期收支三数字、当前项目已花费/预算进度、账单列表本身、预算预警触发 | 写入完成即新 | 写入时同步重算并写入缓存。用 `#Predicate` 下推时间范围，只取需要的行 |
| **L2 · 准实时** | 分类占比环形图、趋势折线、健康分、经营看板全套衍生指标 | 几百 ms 内 | 后台 `ModelContext` 异步算，算完动画刷新；算完前显示上一次的值 |
| **L3 · 懒计算** | AI 复盘、年度报告、导出 | 进页面才算 / 持久化缓存 | 已有 `ProjectReviewCache` 模式，推广即可 |

### 关于"增量累加"（`+= amount`）

理论最优，但编辑、删除、批量导入、iCloud 同步下行的数据每条路径都要覆盖，漏一条就是脏数据且不会自愈。

**本次不做**。先做"写入时整体重算一次并缓存"—— 开销从「每帧 N 次」降到「每次记账 1 次」，拿走 99% 收益、风险接近零。等单个用户账单上万条、单次重算都开始卡了再上增量。

### 推荐的统一刷新信号

在 `AppStore` 增加：

```swift
@Published private(set) var dataVersion: Int = 0
```

任何写操作后 `dataVersion += 1`；各 view 用 `.task(id: store.dataVersion) { await recompute() }`。

**好处**：不需要为每种数据变化单独接线，不会漏刷；且这是给云化做的投资（见第五节）。

### 附：第一批与第二批的关联性

**一句话结论：方向上是"第一批铺路、第二批用路"，但两批改的是不同页面，绝大部分互不干扰。真正需要小心的只有步骤 8b/8c 这一处。**

| 依赖 | 说明 |
|------|------|
| `dataVersion` 机制 | 第一批建立。第二批步骤 2 / 6 直接拿它当刷新信号，没有它就得各自再造一套 |
| `.task(id: dataVersion)` 写法 | 第一批在首页验证过可行，第二批照抄即可 |
| `generatePerfTestTransactions(5000)` | 第一批加的 Debug 工具，是第二批做前后对比的前提 |

#### 第二批**不**依赖第一批的地方

步骤 1（删死代码）、3（统计页算法）、4（新建 Calculator）、5（看板改造）、7（Lifestyle）改的都是第一批没碰过的文件，即使第一批不存在也能独立做。所以两批之间**不存在"第一批改错了会让第二批返工"**的关系。

#### ⚠️ 唯一的强耦合点：步骤 8b/8c 会反向影响第一批

第一批把首页、全部账单页、个人中心、项目卡片**全部挂到了 `dataVersion` 和全量 `refresh()` 上**。步骤 8b 要拆分 `refresh()`、8c 要收窄 `dataVersion` 的触发条件 —— 一旦收窄过头，第一批那些页面就会漏刷，等于把 P0-6 的 bug 复制到首页。

最具体的一个坑：`projectSummaries`（项目卡片的"已花费"数据源）是在 **`fetchProjects()`** 里产出的，但它的内容来自 **transaction**。

```swift
// AppStore.swift:164-198  fetchProjects()
for project in all {
    for tx in project.transactions ?? [] { ... }   // ← 项目汇总其实吃的是账单数据
}
projectSummaries = summaries
```

拆分后如果按直觉写成"记一笔账 → 只调 `refreshTransactions()`"，`projectSummaries` 就不会重算，**首页项目卡片的已花费金额会停在旧值**。正确做法是：任何账单写操作都必须同时触发 `refreshProjects()`，或者把 summary 的计算从 `fetchProjects()` 里拆出来独立成一步。

**因此建议**：8b/8c 单独一个 commit，改完先做一轮完整的写操作回归（记账 / 改金额 / 改分类 / 删账单 / 补往月账，每种都回首页和账单页看数字），确认无误再合。步骤 1~7 可以先行合入，不必等它。

## 六、与《账号体系与数据云化PRD》的关系

### 结论：先修性能，再做云化。顺序不能反。

#### 1. 云化不解决任何一条卡顿

云化 PRD 5.1 节明确写了：

> **本地优先，零阻塞** | App 打开立即展示本地 SwiftData 缓存，绝不等待任何网络操作

即登录模式下 UI 读的**仍然是本地 SwiftData**。读路径一行没变，第二节列的所有问题原封不动。云化换掉的只是"数据从哪来"（CloudKit → 自建服务端），"数据怎么算、怎么渲染"完全没动 —— 而卡顿 100% 发生在后半段。

#### 2. 先做云化会放大现有问题

| 云化机制 | PRD 位置 | 与现状的冲突 |
|---------|---------|-------------|
| `syncedToServer` 上传成功后回写 `true` | 5.3 节 | 每次回写是一次真实 `save()` → `objectsDidChange` → `refresh()` → 全屏重绘。批量上传 50 条 = 50 次触发。比现在系统托管的 CloudKit 批量导入频率**更高** |
| `/sync/pull` 批量 upsert 落库 | 5.5 节 | 进前台拉增量时的集中大写入，会在 pull 期间反复触发 `refresh()` |
| 通知回环 | 5.2.1 节 | PRD 只讨论了**正确性**风险，未讨论**性能**。回环 + 全量 `refresh()` 是卡顿放大器 |

#### 3. 服务端聚合只能帮 L3

首页三个数字必须离线可用，不能依赖网络，所以 L1 的实时统计**必须留在本地算**。服务端聚合真正有价值的是 L3：年度报告、跨设备历史大盘、以及 PRD 第七节那个凌晨 2:00 的画像定时任务 —— 这些本来就可接受延迟。

#### 4. 步骤 8（刷新收敛）是给云化做的投资

把 `AppStore` 改造成「单一变更信号 + 派生汇总层」之后，接服务端时 `/sync/pull` 完成只需要 bump 一次 `dataVersion`，整个 UI 自动正确刷新，不需要逐页面改。

**如果不先做这一步**，云化过程中会被迫在每个页面单独处理"服务端数据回来了要刷新"，工作量和出错概率都会显著上升。

#### 5. 云化会顺带带来的一点改善

登录模式下 CloudKit 被关闭，少了一个 `objectsDidChange` 的触发源。但这是次要收益，不能作为先做云化的理由。

## 八、风险与注意事项

- **不要为了"防止数据不同步"而放弃缓存**。正确的缓存失效时机（写入触发）与现在触发重绘的时机完全一致，不存在时效损失。见第三节。
- **不要用"滚动时暂停渲染/计算"作为主方案**。它治标不治本：滚动停止瞬间攒下的计算会一次性爆发，从"持续小卡"变成"停下来大卡一下"；且实现上只能到处加 `isScrolling` 标志位，代码会变脏。iOS 18 的 `onScrollPhaseChange` 可以用来挂起 L3 级别的昂贵异步任务，属于锦上添花，不是主线。
- **不要一上来做增量累加**。见第四节。
- **改动顺序**：先只改 `DashboardView`，真机对比手感确认思路有效，再往下推。避免大批量改完发现方向不对。
- **每批结束都要用 5000 条数据集跑一次前后对比**，用数据而不是手感来判断是否达标。
- **第二批的步骤 8b/8c 不要和其他步骤混在一个提交里**。它会反向影响第一批已改好的页面，独立提交才好回滚（详见第五节末尾"第一批与第二批的关联性"）。
